# opendata-atlas: knowledge tooling

How portal knowledge is built and kept current: the profiler, drift checks, the contribution path, the curation skill, per-portal evals and knowledge-gap reports. It is part of the design: the rest of the contract is in [design.md](design.md), and the same status and *(Claude's call)* convention applies.

## The profiler

`uv run atlas-profile <host> [--datasets N | --dataset ID ...] [--out DIR] [--report PATH]` (dev CLI, not an MCP tool; `src/opendata_atlas/profiler/`) writes draft pack files.
- `<host>` is a registered portal's id, alias or public host. An unknown host is exit 2.
- `--datasets` defaults to 10 and must be at least 1.
- `--dataset ID`, repeatable, profiles exactly the named datasets in place of the flagships (step 3), so a curator can reach a dataset outside the most viewed. It excludes `--datasets` (exit 2). An id that Discovery (`only=dataset&ids=...`) does not return for the portal's domain writes the report with `error` `datasets: not on this portal: <ids>` and exits 6, with no pack files.
- `--out` defaults to `src/opendata_atlas/portals/<id>` when `src/opendata_atlas/portals` exists under the working directory, and is otherwise required (exit 2). An existing `--out` is exit 2: the profiler never overwrites a pack.
- `--report` writes the JSON report there; without it the report goes to stdout. The report has, per flagship dataset, its title, view count, the ids of its claims, and `notes` saying why a column or probe gave no claim.
- Requests go through `SodaClient`, awaited one at a time.

Steps:
1. Resolve and verify catalog identity (as [design.md](design.md) Registry step 3): up to three Discovery pages with the portal's `catalog_query`, every result carrying its `result_domain`. If identity is not verified, the report is written and the exit code is 3, with no pack files. An upstream failure in steps 1 to 3 writes the report with `error` (`<step>: <code>`) and exits 4, with no pack files.
2. Asset mix from facets: `GET https://api.{region}.socrata.com/api/catalog/v1/domains/{catalog_domain}/facets`, its `datatypes` counts.
3. Pick flagship datasets (or take the `--dataset` ids): one Discovery page (`only=dataset&order=page_views_total&limit=100`), re-sorted client-side by `resource.page_views.page_views_total` descending (missing as 0), then id; the top N. The report's `flagship_basis` says so.
4. Per dataset, the view, then `count(*)`. A dataset with 0 rows is noted and has no column probes. Then:
   - **Large datasets** (#81): at `LARGE_DATASET_ROWS` (1,000,000 rows), computed-region fill and text-group share probes cover the 30 calendar days ending with the primary time column's max date (capped at the profiling date, clipped to its min). The primary is the shared primary-time rule's first column (a reviewed timezone column, else the first time-typed column). Without a usable primary time range, these probes stay whole-table. The window's dates are literals, so drift re-runs the same window; its shares describe recent rows, not all history.
   - **Computed-region columns:** `SELECT count(<col>) AS filled, count(*) AS n` gives a `place_field` observation naming the layer id and the candidate label column. That is the layer view's text or number column that best names each feature: not GIS bookkeeping (`_feature_id*`, `objectid`, `globalid`, `shape_*`, `st_area*`, `st_length*`), and, where the view's cached cardinality is known, with distinct values for at least 90% of the features. Among those, a name containing `name` or `label` comes first, then text before number, then schema order (`label_candidate` in `profiler/profile.py`; ruling 87). A curator still sets `label_column` from the layer's rows. Its assertion is `share_by_group` (`filled` over `n`) with `min` the observed share less 0.05, rounded down to hundredths and at least 0.01 *(Claude's call)*.
   - **Text columns**, the first 20 in schema order: `SELECT <col> AS v, count(*) AS n GROUP BY <col> ORDER BY n DESC LIMIT 101`.
     - **Categorical rule** *(Claude's call)*: only a column with at most 100 groups is observed; the rest are noted as skipped. This narrows the exposure of free text and personal names, but does not rule it out: a small categorical column can hold names. A column whose values are not valid Unicode (a lone surrogate) is noted and skipped.
     - Values in the shared placeholder vocabulary give a `placeholder_share` observation, with no `placeholders` declaration and one `value_present` per value.
     - Values with leading or trailing whitespace give a `padded_values` observation (the padded groups' share of rows), asserted by `value_present` on the most common padded value.
   - **Time columns**, the first 3 time-typed columns, when the portal has a timezone. Run `min`/`max`; a max after today is noted and the window ends today, so a future-dated row cannot move it (decisions row "Profiler: targeted datasets and timezone probes"). If the portal's zone has a spring-forward day in range, take the latest one and probe rows by hour on that day (`dst_gap`, at the hour the zone skips). Always probe rows by hour over the last 365 days of the window, or its last 7 days on a large dataset (`diurnal_peak`, peak hour ± 2); a zone with no spring-forward day in range is noted and gets this probe alone. Then count the window's rows at exactly 00:00:00: when they are at least 2% (`MIDNIGHT_MIN_SHARE`), they may be a default for an unknown time, so the by-hour probe is rerun without them, and the count is recorded as a third probe for the reviewer to interpret. Together they give a `column_timezone` observation, except for a date-only column: when every row of the probes is at hour 0, the dataset gets the note "<col>: date-only; no timezone test applies." and no claim (ruling 52). A portal with no timezone and probes with no rows are noted, with no claim.
   - A probe that fails upstream is noted, and the profiler moves on. A column without a string `fieldName` is noted and skipped.
5. Emit claims with `evidence` and `assertion` blocks and **no `interpretation`**, so everything lands at knowledge level `profiled`. Claim ids are `<dataset id>-<column>-<fill|placeholders|padded|timezone>`.
   - **Assertion rule:** an assertion is emitted only if its checker passes on the profiler's own probe rows. Otherwise the claim keeps its evidence without it.
   - **Tier copy:** `portal.toml` copies the registry identity, its current `tier` included, because `PortalIdentity` requires one. Copying never promotes a tier *(Claude's call)*.
   - Claims go to `facts/<dataset id>.toml`, and layer claims (none yet) to `regions.toml`. Strings are written as ASCII with JSON escapes; a lone surrogate becomes U+FFFD, so every file parses.
   - **Load check:** the CLI writes the files to a temporary sibling of `--out`, loads them with the pack loader, and only then moves them to `--out`. A pack that does not load exits 5, naming the file, and leaves nothing behind.
   - **Value review** (ruling 53): the CLI prints every emitted value outside the shared placeholder vocabulary, with its claim id, to stderr under "Review these values before committing; drop any that identify a person", and the report lists them as `review_values`. The operator must review them before committing a draft.

The profiler never writes an interpretation, reliability, or tier. A reviewer does, in a PR.

## Drift checks

- `uv run pytest --run-integration -m integration` runs every assertion in every pack, and regenerates `validation.json`. The same session runs every pack's guide examples (`tests/test_live.py`, #21), and each must return rows; the curation test also runs a new pack's examples itself, and the contribution path (step 8) runs them by hand. Each guide records `observed_at`, the date its figures were probed; a served guide opens with it, and past `STALE_AFTER_DAYS` (180) asks the agent to re-check counts and date ranges with a query before quoting them.
  - `tests/test_drift.py::test_claim_still_holds` has one case per asserted claim, with id `<portal id>:<claim id>`. `src/opendata_atlas/portals/drift.py` lists those claims from every pack directory that has a `portal.toml`.
  - Each case runs, once and in order, each probe its assertions name; a temporary `query_timeout` retries that probe once before it is `inconclusive`, and no other error retries (#81). A `soql_probe` is sent as `$query` to the claim's dataset (or layer). A `metadata_probe` path is read on the portal's public host. Requests go through `SodaClient`, one at a time.
  - Each case stashes its result and fails unless the claim `passed`. A case whose check raises an unexpected error stashes an `inconclusive` result (detail: the exception type and message) before it fails, so the merge never keeps an older outcome as current. At session end, `tests/conftest.py` writes the `--drift-report` file first, then merges the stashed results into `validation.json` (see Merge and prune in [design.md](design.md)), whether or not any case failed. A malformed `validation.json` or a pack that fails to load makes that merge fail loudly, naming the file, after the report is written. `validation.json` is replaced atomically (a sibling temp file, then `replace()`).
  - `--drift-report PATH` also writes a JSON report: `generated_at`, then per claim its portal, claim id and outcome, and per assertion its checker, probe index, outcome, detail and request (the SoQL text or metadata path).
  - A session that runs no drift case, such as a plain `uv run pytest`, writes nothing.
- `.github/workflows/drift.yml` runs weekly (Mondays 15:41 UTC) and on demand. It runs the drift session with `--drift-report`, then `scripts/drift_issues.py` turns the report into one issue body per portal with a `contradicted` or `inconclusive` claim (a table of claim, outcome, checker, request and detail for each assertion that did not pass). A missing or unreadable report means the run failed before any claim ran (a pack that fails to load at collection, say), and then the one issue is `Drift: run failed`, linking the run's log (final review M-8). A shell loop opens an issue labelled `drift`, or comments on the open one with the same title (`Drift: <portal id>`). The workflow has not yet run on GitHub: until it does, `tests/test_workflows.py` (its shape, and the loop against a stub `gh`) is its only check, and the first scheduled run should be checked by hand.
- The release gate ([design.md](design.md), Validation state and freshness) blocks shipping contradicted knowledge: `validation.gate_failures`, run by `tests/test_release_gate.py`, fails on a `contradicted` claim, a claim `inconclusive` twice running, an asserted claim with no entry in `validation.json`, and an entry whose `assertion_digest` is missing or differs from the claim's current one (an assertion edited without a drift run). An entry for a claim no longer asserted is not a failure; the next drift run prunes it.

## Contribution path

`CONTRIBUTING-portals.md` walks a contributor through: find or register the portal (`atlas_find_portals`; a missing portal is a separate registry PR to `registry_overrides.toml`), run the profiler (`uv run atlas-profile <host>`) and act on its exit code, delete every claim whose `review_values` entry identifies a person (ruling 53), move the identity into the pack (drop the portal's override; set `jurisdiction` only from cited `document` evidence, with `region` the ISO 3166-2 subdivision code without the country prefix, then `timezone` only for a single-zone jurisdiction; a multi-zone jurisdiction leaves `timezone` null and records the zones, and no evidence leaves both null and records why, rulings 57 and 60), review observations, add interpretations with reasons, add `document` evidence where no probe suffices, write a guide per reviewed dataset, write `evals/portals/<pack>.json` with `covers`, keep `tier = "profiled"`, run the checks, promote to `curated` only if it qualifies, and open a PR. The checks are:

- the drift run scoped to the portal: `uv run pytest --run-integration -m integration tests/test_drift.py -k <portal id> --ignore=tests/test_curation_skill.py`;
- the offline gate, where the release gate counts only the curator's pack;
- `uv run python evals/run.py --portal <pack> <out>`, run 3 times.

Another pack's failing claim is never edited and is named in the PR description; "Never edit another pack" wins over every check (ruling 59). **Promotion rule** (ruling 58, matching the Task 15 gate): `curated` requires the offline conditions and, across the 3 eval runs on the submitted pack (after any pack change the checks rerun from the first), every task graded PASS in at least 2 and FAIL in at most 1; otherwise the portal declares `profiled`. It also carries the tier, knowledge-level and validation definitions.

- **Served copy:** the server serves the file as topic `contributing`, one item per `## ` section (`tiers`, `levels`, `validation`, `path`; resources `opendata-atlas://contributing/{section_id}`), so a heading added there must also be added to `_CONTRIBUTING_SECTIONS` in `core/reference.py`, from `src/opendata_atlas/assets/contributing.md`, a byte-identical copy read with `importlib.resources`, because the root file is not in the wheel. `tests/test_contributing.py` fails when the copies differ, when the text omits a step, or when a section exceeds the result budget (a section is never paged).
- **Path rule:** a pack PR touches only `portals/<id>/`, `evals/portals/<id>.json`, `registry_overrides.toml`, `portals/validation.json` and one line of `CHANGELOG.md` under `## [Unreleased]` (`<id>` is the pack directory name). A new pack is user-visible, so its PR carries its own changelog entry, as `AGENTS.md` asks of every user-visible change (#71). *(Claude's call, milestone 3 Task 13: `validation.json` joins the rule, because the release gate requires an entry for every asserted claim and a pack PR adds assertions.)*

## Curation runbook (agent skill)

The contribution path is also shipped as an agent skill, `skills/curate-portal/SKILL.md`, that a Claude Code or Codex agent can follow end to end from the single instruction "curate <portal>", ending in a pack commit on `curate/<pack>` and the printed PR title and body: the agent never pushes or opens the PR, a human does (ruling 63). The skill ships in the repository, not the wheel. The Claude Code and Codex plugin (`plugins/opendata-atlas/`) carries a stub of the same name that, in a clone, reads and follows the clone's `skills/curate-portal/SKILL.md`, and outside one stops. The skill never sets a reliability without a reason and evidence, and never declares a tier its contents do not support (the tier test enforces this), and never raises a tier to `curated` (a new pack declares at most `profiled`; an existing pack keeps its tier): when its 3 eval runs meet the promotion rule it proposes `curated` in the PR body with the per-run grades, which are its own, and a reviewer other than the agent re-grades before promoting (ruling 64). Its `misleading_field` task prompts name neither the column under test nor the dataset it trips on, and when it reviews more than one dataset its tasks span at least 2. Its `in_area` and `relative_date` tasks carry `targets` naming reviewed columns, which `tests/test_tiers.py` checks for `profiled` and `curated` packs alike. When the most-viewed datasets hold no place-and-time dataset, it searches within a fixed bound (6 searches, 10 describes) and profiles a candidate with `atlas-profile --dataset`; when none is found it ends `profiled_without_review` with no paid eval runs. Before the eval runs it checks that every reviewed claim changes what describe serves (`.curation/served-check.json`), and it writes `.curation/outcome.json` (`completed`, `profiled_without_review`, `blocked_engine`, or `no_change` for an existing pack with nothing new to review, which makes no commit) at the end. Rule 13's freeze is recorded as a digest of the pack and its eval file (`scripts/pack_digest.py`) when the eval runs start, and checked before the commit (decisions row "Curation process from the skill evaluation"). It names each engine defect it finds in the PR body and records none in a repository file (#71); it stops when the pack cannot be made right without engine code. It never pushes or files an issue, never changes the pack once the eval runs start (an eval failure becomes a knowledge gap in the PR body, which bounds the paid runs at 3), and calls the server in-process even when opendata-atlas MCP tools are connected, because a connected server, such as the plugin's, runs an installed release that reads its own packs, not the ones being edited. Its working files (profiler reports, a second profiler `--out`, eval output) go under the git-ignored `.curation/` in the repository root: a headless session may not write outside its working directory, which stopped the first run (2026-10-18) at its first command.

The skill is code an agent runs, so it is tested like code. `tests/test_curation_skill.py` (integration) runs only with `ATLAS_RUN_CURATION=1`, so the weekly live and drift runs never start it; it is paid. `ATLAS_CURATION_HOST=codex` runs the curating agent as `codex exec` (workspace-write sandbox with network, the repository's git directory and `~/.claude` writable, no approval prompts), which has no budget option and is bounded only by the timeout; the default is `claude`. The Codex mode has not yet run. The portal is `ATLAS_CURATION_PORTAL`, default `data.honolulu.gov` *(Claude's call: 72 datasets, a US portal, not Chicago; its "Honolulu 311 Reports" has a computed-region place field and a time column, probed 2026-10-18, so the Camden fallback was not needed)*. The test:
1. adds a worktree on branch `curate/test-<date>`;
2. runs `claude -p "Curate <portal> by following skills/curate-portal/SKILL.md."` there with a fixed tool allowlist, `--strict-mcp-config` and no `--mcp-config`, which restricts MCP servers only: the child loads no MCP server from another configuration (ruling 61). Plugins, skills, hooks, the user's CLAUDE.md and memory still load (ruling 65). claude.ai connectors are dropped: the milestone 3 eval run's 35 `system/init` events list no connector and no MCP server but `opendata-atlas`, though this account has connectors (`evals/results/2026-10-18-m3.md`). That run passes `--strict-mcp-config` with `--mcp-config`. The curation command, which has no `--mcp-config`, was observed in milestone 4 run 1: its `system/init` lists 28 built-in tools, no MCP tool and no MCP server (`docs/evidence/curation-chicago-2026-10-19-run1/init-check.json` holds empty `mcp_servers` and `mcp_tools`). The same check flags a synthetic init that lists a connector: `docs/evidence/launch-evals-2026-10-19/known-positive-connector-init.jsonl` (byte-identical to the synthetic init Task 3 used, verified with `cmp`), whose FAIL line is in `restriction-known-positives.txt`. It also passes `--permission-mode acceptEdits` and `--max-turns 200`, under a 3-hour timeout and a `--max-budget-usd 12` cap (ruling 74), with `ATLAS_RUN_CURATION` removed from the child's environment so nothing the agent runs can start a nested curation run (`tests/test_curation_env.py`);
3. requires the transcript to end `subtype: "success"` (for Codex: exit 0 with a last message);
4. requires at least one commit whose paths lie within the path rule, and a declared tier that does not raise the base's to `curated`;
5. reads `.curation/outcome.json`: for `completed`, its `pack_digest` must equal the committed pack's, each of the 3 agent eval runs it records in `eval_runs` (`.curation/<pack>-<date>-<n>/evals-1..3`, so a rerun never overwrites an earlier run's transcripts; `evals/run.py` exits 2 rather than overwrite one, #70) must hold a transcript per task (an unhealthy one is a FAIL grade, not a harness failure), and `served-check.json` must hold a `{claim_id, expected, served, matches: true}` entry for every reviewed claim the run added or changed against the base (#28); the compatibility case's `.curation/compat/partial/outcomes.json` must hold a row for the portal, with every step `ok` when the final message proposes `curated` (#67); and every claim the base pack held must still be there or be named in the final message, as step 11.1's removal of a failing claim requires (#68); for `profiled_without_review` or `blocked_engine`, it needs a `reason` and no eval run directory may exist; `no_change` needs a reason, an existing pack for the requested portal, no commit and a worktree with no change outside the ignored `.curation/` (#29), and ends the checks; `preflight_failed`, `not_registered`, `needs_input` and `profiler_failed` (the skill's stops at steps 0 to 2) need a reason, no commit and the same clean worktree (#69), and end the checks;
6. in the worktree, requires exit 0 from the drift run scoped to the portal and from the offline gate, which for `completed` is the whole suite plus `ruff check`, `ruff format --check` and `ty check` (all of which read untracked files) and otherwise `tests/test_packs.py`, `tests/test_tiers.py` and `tests/test_release_gate.py`; every guide example of the pack to run through the in-process client without an error envelope (no other test runs a new pack's guide examples); and, for `completed` only, the eval file to cover all four kinds and one `evals/run.py --portal <pack>` run to end every transcript `subtype: "success"`;
7. writes `summary.json` (pack, declared tier, outcome, claim counts by kind, each check's exit code, eval answers, the session's cost) to `ATLAS_CURATION_EVIDENCE` when set.

- **Grading:** eval answers are graded by hand against their `expect`, not by the test, because grading needs a judgment it cannot make.
- **Reviewing a produced pack** (milestone 4, scope ruling 2):
  - a fresh reviewer, not the curating agent, reviews the run branch as a PR and records the review in `docs/reviews/<date>-m<N>-<portal>-pack.md` (e.g. `2026-10-19-m4-chicago-pack.md`);
  - the PR is merged only when no Material finding is open, and only by whoever `AGENTS.md` lets merge (#34; in milestone 4 the reviewer merged with `--no-ff`, which is history);
  - nobody hand-edits the pack.
- **Evidence:** each run's summary and diff stat go under `docs/evidence/curation-<date>/` or `docs/evidence/curation-<portal>-<date>-run<N>/` (`<portal>` a short name: `chicago`, `everett`, `king-county`).
- **History:** the curation runs by milestone are in [history.md](history.md#curation-runs).

## Per-portal eval tasks

Seattle's eval tasks found traps that probes alone did not (e.g. pre-2017 crime neighborhoods, which a guide got wrong until the eval run). So every curated portal has its own tasks in `evals/portals/<id>.json`, in the `seattle-open-data` task format, covering at least:
- an "in <area>" count on a reviewed place field;
- a relative date ("last month") on a reviewed time column;
- a field that looks usable but is placeholder-heavy or sparse;
- something the portal does not publish (an honest "not here").

Task files:
- A task has `id`, `prompt` and `expect` (the grading criteria), and optionally `env` (server environment), `server_args` and `covers`.
- `covers` names which of the four kinds above a task is: `in_area`, `relative_date`, `misleading_field`, `not_published`. The tier test reads it to check that a portal's file covers all four.
- `server_args` are appended to the capture server's arguments. The only one is `--validation PATH`, a repository path to a fixture validation file served in place of the shipped `validation.json` (e.g. `evals/fixtures/validation-stale.json`). It is for evals only; the product has no configuration for the validation path.
- Tasks that span portals or test portal choice live in `evals/tasks.json`.
- `evals/run.py --portal <id>` runs `evals/portals/<id>.json`, where `<id>` is the pack directory name, the portal id (`data.seattle.gov`); without `--portal` it runs `evals/tasks.json`.
- *(Claude's call)* Seattle's file holds tasks 01–24, `27-unreviewed-on-curated` and `30-stale-claim`; the cross-portal file holds 25, 26, 28, 29 and `31-knowledge-gap-offer`.

**Promotion to `curated` requires the portal's eval tasks to pass** under the promotion rule (Contribution path: every task PASS in at least 2 of 3 runs and FAIL in at most 1), in addition to the reviewed dataset, guide, and smoke test. An eval failure is read first as a knowledge gap (a missing or wrong claim) and only then as an engine bug.

`evals/run.py` exits 1 when any session exits nonzero (#26). Claude sessions run with `--tools ""`, so only the server's tools exist. Codex sessions run in an empty per-task directory under a clean `CODEX_HOME` that turns off apps, web search, `shell_tool`, browser, computer use and image viewing; codex-cli 0.164.0 keeps `unified_exec` on whatever the config says (`codex features list`), so a Codex session can still run commands, and `evals/report.py` flags, and exits 1 for, any session that called a tool other than the server's (#27).

Each Claude eval session runs with `--max-budget-usd 1` (ruling 74). `claude --help` says only that the option is the "maximum dollar amount to spend on API calls"; whether a session can end above it was not probed, so the cost gate counts each session at its cap. `evals/run.py --host codex` runs uncapped: `codex exec --help` (codex-cli 0.163.0) lists no budget option, so a Codex run is outside the per-session cap and no paid step of milestone 4 uses it. The eval runner gives the agent only the server's tools (`claude -p --tools ""` plus the server's MCP tools; for Codex, the clean `CODEX_HOME` `seattle-open-data` already uses). `--allowedTools` alone pre-approves tools without restricting them: in a 2026-10-17 comparison run, agents used Bash in 13 of 48 tasks until `--tools ""` was added.

## Knowledge-gap reports

The server cannot report usage, so gaps found in use reach the project through the user, as defects already do. The defect head rule is widened to cover knowledge gaps: a field, timestamp, or dataset that misled the agent, or knowledge the answer needed that was missing (no reviewed place field, a stale claim, a placeholder the pack does not declare). The tracker is public, so nothing is filed unasked. Three obligations:

1. **Head rule and notice:** the agent offers the user a **knowledge-gap** issue on the tracker, with portal id, dataset id, column, and what was wrong, and never files one unasked. The head rule states this. Every fired `knowledge_notice` restates it at the point of use, ending with: "When you caveat a gap named here, also offer the user a knowledge-gap issue (capabilities ## Knowledge gaps); never file one unasked." (Why the notice carries it: decisions log, rulings 68 and 70.)
2. **Capability summary:** its `## Defects` section gets a `## Knowledge gaps` sibling defining what qualifies (it is not the publisher's data quality as such, but the server's missing or wrong account of it).
3. **Label:** issues carry the `knowledge-gap` label, which is the curation queue.
